# RAG 改造决策监控协议

- 建立日期：2026-08-11
- 目的：避免将超出用户合理认知负担的技术判断交给用户，也避免主执行 Agent 自评自证
- 适用范围：语料、检索、Graph、Prompt、评估、索引迁移和发布阶段门

## 1. 角色分工

### 主执行 Agent

- 收集证据并提出推荐；
- 维护计划、实现和验证；
- 明确事实、推断和产品选择；
- 遇到阶段门阻断时停止实现。

### 决策监控 Agent

- 独立读取计划、代码、测试和结果；
- 检查循环论证、指标错配、样本污染和范围膨胀；
- 判断是否把技术责任错误转交给用户；
- 输出 `APPROVE / APPROVE_WITH_CHANGES / BLOCK`；
- 不参与被审查实现，不修改业务代码。

### Conrad

只决定真正的产品语义和价值取舍，例如：

- 什么用户任务更重要；
- 什么叫“热门”或“值得关注”；
- 可接受的响应速度、成本和失败体验；
- 是否接受某项产品风险。

Conrad 不负责判断：

- relevant URL 是否完整；
- scorer 是否正确；
- seam 和测试切片是否充分；
- 数据库/索引实现细节；
- 是否存在循环论证。

## 2. 强制审查点

以下动作执行前必须经过监控 Agent：

1. Gold 数据集晋级；
2. 评估器新增或修改指标；
3. 单日影子语料进入候选索引；
4. Graph schema 扩展；
5. Prompt Registry 接入正式回答链；
6. 历史索引重建；
7. 候选 generation 切换为正式 generation；
8. 对外宣称质量提升或达到发布标准。

以下产品语义变更也必须在写业务代码前审查，不能等实现完成后补问用户：

9. 新增或改变查询任务、路由标签及覆盖顺序；
10. 新增“重要、热门、相关、可信、最新”等产品判断字段或排序公式；
11. 改变新闻主榜、补充项、历史背景和排除项的准入边界；
12. 改变内部检索、GraphRAG、联网搜索之间的触发与降级关系。

## 3. 审查问题

每个阶段门至少回答：

1. 结论依赖哪些可复核事实？
2. 主 Agent 是否同时定义答案、实现评分并证明自己正确？
3. 指标是否真的对应产品行为？
4. 是否有更低成本的验证路径？
5. 是否把诊断样本混入正式总分？
6. 是否可回滚、可停止、可解释？
7. 哪些问题确实需要用户做产品判断？
8. 当前指标背后的产品语义是否已由用户确认，而不是由实现者默默假设？
9. 是否查阅了与该架构决策相关的一手行业方案，并说明为什么采用或不采用？
10. 是否检查了完整用户路径，而不只是单元测试和内部数据结构？

## 3.1 架构决策前置门

当变更涉及路由、排序、领域标签、Graph schema、证据充分性或联网策略时，主执行 Agent 必须先完成：

1. 代码与失败样本证据；
2. 小而具体的产品语义澄清；
3. 一手资料方案扫描；
4. 备选方案、成本、用户影响与可逆性说明；
5. 不接正式索引的小样验证设计。

缺少任一项时，监控结论不得为 `APPROVE`。

## 4. 阶段门语义

- `APPROVE`：证据、合同与验证充分，可按计划执行；
- `APPROVE_WITH_CHANGES`：允许执行，但必须先完成列出的有限修正；
- `BLOCK`：当前实现会产生不可解释结果或错误风险，必须停止。

监控 Agent 的结论是阶段门证据，不替代主 Agent 的最终责任。主 Agent如不同意，必须写明反证，不能静默绕过。
