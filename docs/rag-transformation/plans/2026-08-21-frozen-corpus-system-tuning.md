# 2026-08-21 固定语料系统调优计划

## 决策

当前阶段停止新增、同步和重新导入语料。所有 Query Contract、检索、重排、Prompt、回答与
用户流程调优，都以同一活动索引为基线：

- generation：`gen-20260821T074117-404548ad`
- latest corpus date：`2026-08-21`
- ChromaDB：`4133` chunks
- retriever：`hybrid`
- runtime corpus mode：`frozen`

这份冻结只约束 RAG 正式语料；测试问题、Gold 标注和诊断记录不是语料，不会进入索引。

## 为什么这样做

如果语料、索引和策略同时变化，就无法判断分数变化来自数据还是系统。固定语料后，每次
变化只有一个主要变量，可以低成本比较旧版与新版，并避免自动同步污染 Blind/Eval 证据。

需要明确边界：良好架构可以让普通新增语料不再要求修改代码，但不能保证任何未来数据都
天然合格。未来更新仍必须经过 staging、质量门、影子索引、原子切换与回滚，异常数据进入
隔离区而不是修改生产架构来迁就。

## 执行顺序

1. **运行时冻结**：启动时不同步、不入库；系统状态明确显示 frozen。
2. **Query Contract**：完成 v3.5 的公共语义 seam 修复，只用既有可见校准和回归资产。
3. **检索与重排**：固定 Query Contract 后，按 A–E 路由分别测召回、分层和排序。
4. **Prompt 与 Answer Envelope**：只消费同一 Route Contract 和结构化证据。
5. **端到端 Gate**：Docker + Web UI + DeepSeek 的真实用户路径验收。
6. **自动更新（以后）**：独立设计 managed 模式，验证通过后才允许从 staging 切换索引。

## 每阶段 Gate

- 先写一个能暴露根因的小样；一次性明确输入、预期和停止条件。
- 小样没有方向性提升，不扩大实现范围。
- 通过后才运行既有回归；不反复消费 Blind，也不靠调参追逐单题。
- 质量监管同时检查代码合同、产品任务和用户流程，不只看测试是否为绿。

## 明确暂停

- 上游自动同步与新增日报入库；
- 全量索引重建；
- 新框架、新 Router、新 UI 功能；
- 自动更新 GitHub Action 的正式接入；
- 与当前主线无关的重构。
