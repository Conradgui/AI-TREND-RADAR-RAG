# 查询路由与新闻排序方案层复盘计划

- 日期：2026-08-13
- 状态：产品语义已确认；合同已固化；尚未授权正式链路替换
- 目标：判断当前“任务路由—候选召回—新闻筛选—排序—证据回答”链条是否建立在正确的产品语义和行业方法上，并给出更优且可渐进迁移的体系。

## 成功标准

1. 用代码证据说明当前系统真实如何工作，而不是依据文档宣称。
2. 用一手资料复核多阶段检索、查询路由、RAG 自适应检索、GraphRAG 和新闻排序的成熟做法。
3. 明确区分稳定事实、查询相关判断与展示策略，避免把“内容是什么”“是否是新闻”“对当前问题是否重要”混成一个标签。
4. 给出适合当前项目规模的推荐链路、暂不采用项、迁移顺序和成本边界。
5. 复盘为什么此前没有在架构决策前完成产品澄清与外部调研，并补上可执行的防复发门禁。

## 研究问题

- “重要新闻”应是内容固有标签，还是查询相关的动态判断？
- 用户意图、主题相关性、新闻性、重要性、新鲜度、来源可信度应如何分层？
- 何时使用关键词、向量、重排模型、LLM、图谱和联网搜索？
- GraphRAG 在单条新闻排序与跨事件趋势分析中的边界是什么？
- 当前项目是否需要引入现成路由框架或学习排序模型？
- 如何以小样验证方案，而不是直接全量改造？

## 工作步骤

1. 复核 `query_understanding.py`、`retrieval_gateway.py`、`retrieval_planning.py`、`prompt_registry.py` 及相关评估结果。
2. 独立研究 Agent 调研官方文档、原始论文和官方源码。
3. 对照项目形成：现状图、目标链路、决策矩阵、迁移阶段与 Stage Gate。
4. 更新决策监控协议，使产品语义与用户流程成为架构变更的强制审查项。

## 明确不做

- 不调整权重、关键词或 Prompt。
- 不接入新框架。
- 不重建索引。
- 不根据少量样本宣称质量提升。

## 2026-08-13 产品确认

Conrad 已确认放弃全局永久的“重要新闻”判断，正式采用以下顺序：

1. 根据当前 Query Frame 将候选分为 Primary、Supplementary、Background、Unverified 或 Excluded；
2. 只在同一层级内部按照 Dynamic Importance、Query-relative Freshness 和 Evidence Quality 排序；
3. 热度、新鲜度或来源声望不得把弱相关内容跨层推入主答案。

该决策已记录在 `docs/adr/0005-relevance-tiers-precede-within-tier-ranking.md`，完整合同见 `docs/rag-transformation/specs/query-evidence-routing-contract-v1.md`。

## 下一阶段：冻结小样与影子接口

1. 从现有已人工裁决样本中整理 12–20 条开发/校准样本，补足跨问题角色变化样本；
2. 从不同日期建立独立冻结盲测集，实现和调参阶段不可见；
3. 先写分层评估器的辨别力测试，确保正确分层优于层级退化和错误分层；
4. 以影子模式实现 `QueryFrame` 与 `EvidenceBundleV2`，不接正式回答链；
5. 对相同问题并行运行旧链路和新链路，报告质量、延迟和成本差异；
6. 由质量监管 Agent 执行 Stage Gate，再决定是否进入正式替换。

## 第一次独立监管结论

- 结论：`APPROVE_WITH_CHANGES`；产品方向通过，正式实现暂缓。
- 已补充：唯一接口版本、分层/排序职责、旧语义迁移、校准/盲测隔离、成本预算和功能开关回滚合同。
- 下一步：对合同做一次复审；只有得到 `APPROVE` 才进入影子实现。
