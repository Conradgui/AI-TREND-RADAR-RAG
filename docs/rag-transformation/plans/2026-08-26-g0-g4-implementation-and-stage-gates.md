# G0–G4 收敛实施计划与 Stage Gate

> 版本：v1.6 · 日期：2026-09-01 · 状态：G0、G1、G2 已通过，G3 自动更新、真实容器与 clean clone 验证已完成，Runner/单日期 canary 证据仍待执行。
> 依据：[全局缺口与后续收敛基线](2026-08-26-global-gap-and-closure-baseline.md)。
> 本文是执行合同（目标、边界和验收口径），不是完成证明。G3 的自动更新实现已进入受控验证，
> 但在真实 Runner、失败恢复和单日期 canary 证据完成前，不宣称 G3 通过，也不扩大来源或数据量；不重建 Neo4j/数据卷。

## 1. 目标与非目标

### 1.1 目标

把现有 AI Trend Radar RAG 收敛成一条可验证的产品链：用户问题经过确定性快速识别，必要时才做受限语义理解；检索结果按相关性层级、重要性、新鲜度和证据质量排序；Agent 只使用可追溯证据；日报条目保持独立身份；主体关系可以从候选变成有证据的可复用知识；数据更新可以失败、恢复和审计。

### 1.2 非目标

- 不从零重写现有 A–E 路由、原子入库、Answer Envelope 或 Web UI。
- 不把周报、月报加入主向量库或图谱；它们仍是浏览制品。
- 不默认引入 LangGraph、RAGAS 或新的向量数据库。只有现有实现无法满足已定义验收项时，才做限时替代方案评估。
- 不把“模型回答得像”当成关系事实；不存储思维链，不把完整对话回灌为证据。
- 不在未有当前版本基线和回滚方案时解除正式语料冻结。

## 2. 执行规则

### 2.1 变更顺序

```text
G0 冻结与可复现基线
  ↓
G1 主体解析、候选关系证据与受控复用
  ↓
G2 检索排序、Prompt/答案契约、性能与实际用户流程
  ↓
G3 自动同步、双库一致性与真实 Runner
  ↓
G4 干净目录发布验收与开源交付
  ↓
G5（未来）带来源的研究成果沉淀与知识产品化
```

G1 和 G2 共享同一套冻结评估输入，但 G3 以前不宣称无人值守更新已验收；G4 以前不宣称发布就绪。

### 2.2 角色与效率

本计划采用单一主线执行，避免多个代理同时修改同一文件。主会话保持 medium 档位，负责产品目标、范围和阶段判断；若后续可用，Sol 只负责架构/合同复核，Terra 负责阶段质量与用户流程复核，Luna Max 只执行明确文件范围内的实现。每次委派前要核实真实模型和权限；核实不了就不声称已完成委派，改为主会话自审。

每个实施包必须写明：目标、问题 ID、允许修改的文件、接口不变量、排除项、测试命令、成本上限和停止条件。一个阶段只有一个写入者；质量复核只读。

### 2.3 证据规则

- 所有数字注明数据集、版本、样本数、时间和评分口径；不能拼接旧评测分数。
- 计划阈值是“放行目标”，不是当前成绩；G0 先固定数据和版本，再执行。
- 失败三次仍无新证据时暂停并报告阻塞原因，不反复重试。
- 每个 Gate 输出 `plan / command / result / decision / next`，并保留原始 JSON、日志或截图路径。

### 2.4 合并后的交付包

为避免把同一个产品问题拆成大量微小停顿，后续只按以下三个包推进：

1. **G2 证据闭环包（当前）**：封存真实任务集、采集一次运行快照、分任务评分、只修首要瓶颈、做一次回归与浏览器复验，然后 Gate。
2. **G3 单日期更新包**：一个新日期从来源进入规范化条目，获得 ATR 和内容指纹，写入影子向量/图 generation，完成一致性检查和回滚演练，然后 Gate。
3. **G4 干净部署包**：固定 main 提交做干净 clone，一键配置/启动/恢复，完成真实用户主流程和文档验收，然后 Gate。

每个包内部允许连续完成必要小步骤，不逐项停顿。每个包最多进行一次“诊断后修复”循环；仍不达标则报告残余瓶颈，不继续堆规则或测试。

G2 内部不再拆成独立项目，只保留三个连续切片：

1. **确定性快路径**：澄清、主体解析、ATR/标题/描述导航和清晰任务路由；目标是零模型或一次受限 fallback。
2. **受控 Agentic 路径**：仅复杂问题允许分解、选择检索工具、检查证据缺口并最多一次纠偏；每步受次数、时间、来源权限和 Evidence Ledger 约束。
3. **分层验收**：检索、Agent 执行、生成和用户完成率分开记分，一次性形成 Gate 证据。

## 3. 公共数据与验收合同

### 3.1 质量硬不变量

1. 每条日报原子条目有稳定 ATR、日期、标题、来源、证据链接和可追溯原始位置；原标题超链接不被 ID 展示破坏。
2. 主向量索引不重复摄入日报 Markdown；周报、月报只浏览。
3. 缺摘要明确标记缺失或补全来源，不能把推荐理由伪装成原摘要。
4. 关系至少带主体、关系类型、方向、来源、证据定位、有效时间、创建时间、版本和状态；没有证据的候选不能进入已确认关系投影。
5. 图库、向量库和活动索引的健康状态不能在未验证时显示为已就绪；更新失败必须可诊断、可回滚。
6. 引用必须回到具体条目或外部 URL；“相关但无法证明”必须进入补充/待核实层，不能进入主答案。

### 3.2 评估输入

G0 固定三组输入：

- **诊断集**：现有 8 条主体关系样例，仅用于发现问题和回归，不能算独立成绩。
- **小型校准集**：12 条覆盖 A–E、主体别名、趋势、负例和证据不足的任务，用于冻结规则和调试。
- **独立盲测集**：使用全新日期的 10–20 条问题/条目，创建后封存；在所有调参完成前不得读取其标签或用其调参。若暂时没有新日期，Gate 不得伪装通过，只能标记阻塞。

每个任务需要标注：问题类型、期望主条目、可接受补充、背景条目、应排除项、是否应联网、时间约束、证据要求和跳转目标。检索 Precision/Recall/F1 只在有明确相关集合的任务上计算；趋势任务另计覆盖、来源多样性、新鲜度和时间线连续性，不能把所有任务压成一个虚假的全局分数。

### 3.3 建议放行目标（G0 后冻结）

这些是工程目标，不是现状声明：

| 维度 | G1/G2 建议门槛 | 说明 |
|---|---:|---|
| 精确条目导航 | 目标条目 Top-5 命中率 ≥ 90% | 另验 ATR/标题直达和侧边栏定位 |
| 标注检索集 | Precision@5、Recall@5、F1 分别报告；主答案层不得混入排除项 | 不对无标签问题计算 |
| 趋势任务 | 主答案覆盖标注核心信号 ≥ 80%，且至少两条独立证据或明确不足 | 关系分析可安全收口，不以“有结果”代替正确 |
| 新鲜度 | 有明确“最近/最新”约束时，过期证据不得冒充当前主答案 | 具体天数由任务标签给出 |
| 证据完整性 | 引用可解析回具体 ATR 或外链 ≥ 95% | 失败样本必须逐条解释 |
| 路由 | A–E 任务分类正确率 ≥ 90%，高风险歧义不得静默误路由 | 小样先看混淆矩阵 |
| 性能 | 热路径 p95 与超时率在 G0 实测后设定；任何路线不以无限延长超时掩盖瓶颈 | 分冷启动、热启动、是否联网 |

若样本量不足以稳定支持百分比，报告原始计数和置信限制，不制造精确度假象。

## 5. G1：主体解析、关系证据与受控反哺

### 产品结果

用户输入中的 Claude/Anthropic、ChatGPT/OpenAI、Gemini/Google/Google DeepMind、Grok/Grok Bot/xAI、SpaceX/X 等可走确定性别名和主体集合快速路径。集合未命中时，才对“未知主体”做一次有边界的 AI 解析；解析结果先是候选，不自动成为事实。候选通过来源证据检查后才可复用，并可撤销。

### 方案边界

- 复用现有 `entity_identity.py`、`entity_registry.json`、`query_route_resolver.py` 和图谱投影接口，不另建一套实体系统。
- 将关系状态拆为 `candidate / verified / rejected / revoked`，为 verified 补齐证据定位和版本字段。
- 建立最小持久化反馈记录：规范主体、别名、关系类型、证据 URL/ATR、解析器版本、时间和状态；不存思维链和整段对话。
- 缓存只复用主体解析，不复用“最新新闻答案”；带 TTL、上下文/版本键，冲突和低证据候选留在隔离区。
- 图谱投影采用批量、幂等、可回滚流程；启动/更新时显式报告版本，不把 `ON CREATE` 误当成全量校准。

### 测试与预算

先用 mock/本地夹具完成 12 条校准集和负例；最多 1 次小规模真实模型调用验证未知主体路径（若环境已授权），不进行全量 API 测试。每个样本最多一次解析、一次证据核验；总调用上限在执行前写入日志。

```bash
python -m pytest -q rag/tests/test_entity_registry.py rag/tests/test_entity_match_ranking.py rag/tests/test_entity_registry_projection.py rag/tests/test_query_signal_and_route_resolution.py
```

### Gate G1

通过条件：已知主体不需要模型即可命中；未知主体不会阻塞普通查询；别名不会破坏主体边界；候选关系不能绕过证据状态晋级；撤销和版本变更不会留下已确认脏投影；12 条校准集按预先标签达到 G0 目标或逐条解释差距。失败时不扩充实体集合、不重复调用模型，先修合同或停在 G1。

## 6. G2：检索、排序、Prompt、答案与用户流程

### 产品链

```text
Query
 → 确定性意图/主体识别
 → A–E 路由与 query rewrite（可解释、可跳过）
 → 向量 + 关键词 + 图检索
 → 原子条目去重
 → 相关性层级：主答案 / 补充 / 背景 / 待核实 / 排除
 → 层内按重要性、新鲜度、证据质量、上游分排序
 → 按任务 Prompt Registry 封装
 → Agent
 → Answer Envelope
 → Markdown/UI 渲染与具体跳转
```

### 关键工作

- 不重做 A–E 路由；补齐路由混淆、热门趋势中的关系信号、证据不足和多步任务覆盖。
- 将“相关性优先”落实为可测试的排序字段，而不是让全局热度覆盖任务意图。
- 只对原子条目去重；修正 ATR/标题/日期/来源的引用映射，保证侧边栏搜索命中后直接定位条目。
- 外部搜索在许可时才触发；搜索结果标记外部、按日期和来源质量过滤，外链引用独立于本地 ATR。
- 保留“思考中”进度反馈，但不泄露思维链；区分真实流式事件与完整答案分块。先缩短不必要的模型参与，再考虑更复杂的流式协议。
- 对热门趋势允许图谱关系查询，但禁止由共现直接推出因果；纵向时间变化和横向主题关系分别标注。
- 保持摘要原始展示逻辑，不加折叠，不因 UI 便利改写空摘要。
- Agentic RAG 不是默认路线：单条导航、单索引事实查询和首页推荐问题优先走固定 Workflow；跨来源比较、复杂时间线、证据缺口补查才允许 Agent 规划和迭代。
- Agent 的在线状态只保留当前请求所需的 Route Contract、工具结果、预算和 Evidence Ledger；跨请求复用的主体关系必须经过候选→核验→版本化持久化，不把整段对话或思维链写入长期记忆。

### G2 诊断顺序与触发实验

先按固定顺序定位问题，禁止从“换模型”开始猜：

1. **输入层**：ATR 原子条目、标题、摘要、日期、来源和证据链接是否完整且未被 Markdown 重复入库；
2. **召回层**：正确 ATR 是否进入候选集，关键词/向量/图各自贡献什么；
3. **排序与准入层**：主答案、补充、背景是否正确，噪声是否挤占上下文；
4. **生成层**：结论是否逐项受 Evidence Ledger 约束；
5. **产品层**：用户是否得到可理解、可追问、可跳转且延迟可接受的结果。

Agentic 路径额外按固定顺序诊断：路由是否应该进入 Agent → 工具选择是否正确 → 是否在首轮证据足够时及时停止 → 纠偏是否带来新证据 → 最终答案是否只引用 Ledger。不能用“Agent 最终有回答”掩盖无效循环、错误工具或超预算。

可选技术只在对应指标失败时做小样对照：Recall/Hit@K 低才比较 Query Rewrite、召回通道或 Embedding；MRR/主答案精度低才比较 Rerank；关系/时间演化题失败才调整图检索；忠实度失败才加强 Claim–Evidence 校验。父子切块仅用于未来长正文证据，日报原子条目不使用通用固定窗口重复切分。任何实验先在固定小样上证明收益，再决定是否进入正式链路。

### 小批量验证

在冻结索引上先跑校准集，不动正式数据；比较旧/新路由的原始结果、排序、引用和耗时。只有小批量达到门槛，才允许使用独立盲测集做一次验收；盲测结果出来后不得再用同一集调参。

当前 G2 收尾不再拆成多个独立里程碑：用经用户确认的 12 条真实语料任务采集一份不可变响应快照，按导航、趋势、关系/时间线、证据不足分别报告；若失败，只选择影响样本最多且能被单一模块解释的一个根因修复。修复后重跑同一回归集用于确认，不把它重新称为盲测成绩。

```bash
python -m pytest -q rag/tests/test_product_query_routing.py rag/tests/test_retrieval_gateway.py rag/tests/test_prompt_registry.py rag/tests/test_answer_envelope.py rag/tests/test_eval_retrieval_precision.py rag/tests/test_eval_answer_policy.py rag/tests/test_chat_stream.py
```

再做实际 UI 只读/低成本流程：日报打开、ATR 直达、侧边栏精确搜索、三项筛选、Agent 热门趋势、关系问题、外部引用、Briefs、System readiness。每条记录截图/请求和结果。

### Gate G2

通过条件：A–E 路由与 Prompt/答案契约不丢失；精确条目和热门趋势分别达到对应门槛；引用可跳转到准确条目；排序先按相关层级再按层内信号；Agent 不把证据不足说成结论；热/冷延迟与超时有当前版本数据；UI 主路径无已知 404/死按钮。否则只修最小瓶颈，不进入自动同步。

**2026-09-01 收口结果：PASS。** 当前活动 generation `gen-20260831T083806-39f9d2a6`（ChromaDB 4286 条）上，12 条经用户确认的真实语料任务全部成功请求并通过分任务验收：`recent_trend 4/4`、`item_navigation 4/4`、`evidence_insufficiency 2/2`、`relation_comparison 1/1`、`timeline 1/1`。本 Gate 不发布跨任务全局 Precision/Recall/F1；原始快照与评分见执行记录中的链接。G3 的本地自动同步、双库一致性和 clean clone 已有证据，仍需 GitHub Runner 与单日期 canary。

## 7. G3：自动同步、双库一致性与真实 Runner

### 产品结果

用户只部署一个仓库即可默认同步上游公开 Pages 制品；进阶用户可在同一仓库切换自维护来源和 Secrets。日报进入规范化、清洗、摘要/缺失标注、稳定 ATR、原子向量和图谱；周报/月报仅发布浏览。失败可重试、隔离、回滚并留下证据。

### 关键工作

- 先验证 `.github/workflows/rag-corpus-sync.yml` 的真实 Runner，再处理 `corpus-producer-self-managed.yml` 的可选分支；不假设本地测试等于 GitHub 端通过。
- 让工作流输出每条条目的 manifest、质量报告、索引 generation、图/向量日期及失败原因；PR/合并 SHA 可追踪。
- 在现有“先 vector-only、再图更新”的安全降级基础上补齐活动 generation、租约、回滚和跨库逐条覆盖检查；自动更新统一走 app 进程内的 `_run_corpus_update_once`，日期集合一致不足以证明每条一致。
- 只在 G2 通过后，用一个新日期做受控 canary；成功后再决定是否解除 G3 验收冻结。Docker 的周期轮询不阻塞聊天，也不创建第二个常驻进程。

## 10. 风险、停止条件与回滚

| 风险 | 识别信号 | 行动 |
|---|---|---|
| 语料/索引版本漂移 | 同一命令得到不同活动 generation | 停止评测，重新冻结并记录版本 |
| 关系误判扩散 | 候选进入 verified 无证据 | 回滚投影，保留候选，修状态转换测试 |
| 模型拖慢热路径 | 无模型即可完成的任务仍调用模型 | 先修确定性路由；不以增加超时解决 |
| 指标虚高 | 小样本百分比很高但原始错例不清 | 报原始计数，扩大或重建标签集 |
| 双库部分成功 | 日期一致但条目/ATR 缺失 | 保留旧 generation，进入 degraded，禁止切换 |
| UI 与后端脱节 | 静态页面显示正常但 `/health` 失败 | 显示真实状态并暂停发布验收 |
| 计划过度工程化 | 为解决一个问题引入新框架/多层缓存 | 退回现有接口，先完成最小闭环 |

任何阶段出现密钥泄露、活动索引不可回滚、生产数据被误删、无法区分测试输入或真实 Runner 权限不明，立即停止并请求用户判断。
