# 检索质量评估与退化诊断计划（2026-08-07）

## 1. 本轮目标

针对用户问题“最近有什么热门趋势？”出现零召回的退化，建立一套可重复、可审阅的评估基线，并回答：

1. 当前检索的 Precision、Recall、F1 到底是多少；
2. 零召回是语义检索质量问题，还是运行时故障；
3. 后续优化应该先修稳定性、排序、数据质量，还是回答生成。

## 2. 已确认事实

- 当前 Chroma 中存在近期 `topic_candidate` 数据；14 天窗口和组合 metadata filter 均可在新客户端中返回结果。
- 长期运行的服务进程曾记录 `Error finding id`，但 `HybridRetriever` 将该异常吞掉并降级为空列表。
- 仅重启 app 进程、不重建索引后，同一问题恢复为 5 条内部引用。
- 因此本次用户可见故障的首要根因是“热更新后的 Chroma 句柄失效 + 检索异常被误报为空语料”，不是知识库真的没有内容。

## 3. 评估边界

本轮拆成两个互不混淆的轨道：

### A. 健康态检索质量

在确认 Chroma/Neo4j 可查询的前提下，只评估检索层，不调用 DeepSeek，避免模型生成波动污染检索指标。

### B. 热更新稳定性

验证数据更新前后，长期运行的服务是否仍能查询；检索异常是否能被识别为 `error`，而不是伪装成 `empty`。

## 4. 数据集设计

- 版本：`retrieval-quality-dataset-2026-08-07.json`
- 语料快照：以当前索引截至日期和索引统计为指纹。
- 问题类型：近期趋势、公司/实体、技术主题、来源限定、精确标题、无答案边界。
- 标签：优先用 canonical URL；URL 不可用时才用 `date + source + title`。
- 标签来源：第一版为“可审阅银标集”，由仓库和索引证据预标，明确保留 `needs_human_review`；人工确认后才可升级为 gold。
- 避免自证：不使用“标题包含查询词即算相关”作为最终真值。

## 5. 指标定义

| 指标 | 白话含义 | 本轮用途 |
|---|---|---|
| Hit@K | 一道可回答问题是否至少找到一条正确证据 | 对外可称“查询成功率”，不冒充分类 Accuracy |
| Precision@K | 返回结果中有多少是真的相关 | 衡量噪声 |
| Recall@K | 应找出的相关证据中找回了多少 | 衡量漏召回 |
| F1@K | Precision 与 Recall 的调和平均 | 单值概览 |
| MRR | 第一条正确证据排得是否足够靠前 | 衡量首屏体验 |
| NDCG@K | 高相关证据是否排在低相关证据之前 | 衡量排序质量 |
| 正确拒答率 | 无答案问题是否没有伪造内部证据 | 衡量边界安全 |
| 检索错误误报率 | 运行时异常是否被错误标记为空结果 | 衡量可观测性 |

同时报告 macro（每题等权）与 micro（每条文档等权），避免大相关集问题支配结论。

## 6. 验证表

1. 固化数据集 → 验证：每题有查询意图、时间窗、相关文档 ID、标签来源和审核状态。
2. 实现纯检索评估器 → 验证：单元测试覆盖 TP/FP/FN、无答案、分级相关性和空返回。
3. 跑健康态基线 → 验证：输出逐题结果、macro/micro 指标和原始检索项。
4. 跑热更新稳定性复现 → 验证：记录更新前后状态与错误分类，不把异常计作语义零召回。
5. 形成优化方案 → 验证：每项优化对应一个失败指标和可回归验收条件。

## 7. 决策约束

- 不为了提高分数修改标签。
- 不把 LLM 回答流畅度当作检索相关性。
- 不在基线完成前大改召回算法。
- 首次报告必须披露标签仍需人工复核的证据边界。
